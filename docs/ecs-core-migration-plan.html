1原则：把“整理”定义成可验收的行为

四条硬规则

  • 行为非冻结，但必须报告：内容未上线、版本未稳定，整理阶段默认可不改行为；若必须改，在提交与汇报中单列（改了什么、影响哪些命令/数值/测试）。
  • 一阶段一提交：每阶段结束时工作树干净、clippy 通过、docs_check 通过、gate 全绿；出问题 git revert 整阶段回退。
  • 单一写者不变：整理不能把“唯一定案 / 唯一落地 / 唯一装配”拆成两条路径。
  • 拆分必须有判据（见下表）；不新增 crate，除非判据 + 使用面两者都满足。

判据表（满足任一才动刀）

  • 大文件：源文件 >800 行且含 ≥2 类流水线职责/阶段。
  • 空壳目录：只做 re-export 或只有一个函数，且没有独立阶段语义。
  • 测试文件：>800 行且可按主题分组。
  • 死代码：生产路径 0 引用（archive、注释不算）。
  • 依赖倒挂：纯规则/数据反向依赖运行时模块。

验收口径

  • 整理阶段：测试组数只增不减，ecs_core 全绿，soak 6 种子「异常：无」。
  • 新增能力阶段：先有测试与 DESIGN 条目，再有实现。
  • 每阶段写一行 REFACTOR.md；涉及取舍写 DESIGN；数值只进 GAME.md。

恢复死代码可见性

  • 本轮 11 处死代码之所以长期没人发现，根因是 lib.rs 的 18 个 pub use * 让 dead_code 失效。
  • P2 起把公共导出改显式，并把引用计数脚本留作阶段自检。
