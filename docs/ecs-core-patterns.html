不是按 GoF 硬套，而是把仓库里反复出现、承担明确职责的组织手法识别出来，标注它们的变体、代表实现与风险。

2模式清单（按职责分组）

A. 组织与数据：内容怎么写进世界

注册表 Registry / Table Module 清晰

静态数据表 + 启动期校验，是全部内容定义的源头。
变体
JSON 内嵌 + LazyLock（物品、法术）；编译期静态表（属性词表、地块属性、怪物卡、容器布局）。
代表
item/registry.rs:78-83 ITEMS / spell/mod.rs:42-47 SPELLS / rules/stat.rs:151 STATS
  • 好处：内容与代码分离、加载失败即启动失败、可反查名字。
  • 代价：改数据要重编译；schema 版本需要手动维护。

蓝图 + 装配器 Prototype / Factory 清晰

蓝图只描述数据，进世界时由唯一装配桥转成运行时组件，避免"两处真源"。
变体
物品实体装配（spawn_item_assembled）；ItemSpawner 同时适配 Commands 与 &mut World（适配器）。
代表
item/mod.rs:242 trait ItemSpawner / item/mod.rs spawn_item_assembled
  • 好处：组件形状集中一处；测试/读档走同一条装配路径。
  • 代价：装配桥是强耦合点，新增部件要同时改数据与装配。

词表 + 解释器 Vocabulary / Interpreter 清晰

用数值 id + 算子表达"任意属性修正"，而不是给每个属性加字段。
变体
StatId 词表 + ModifierOp 三算子；SpellEffect、BehaviorEffect 两个效果词表；ItemPart 部件词表。
代表
rules/stat.rs / rules/modifier.rs / item/registry.rs ItemPart
  • 好处：新增属性/部件不需要改公式代码；解释器（折叠函数）集中。
  • 代价：id 是弱类型，错配只有加载期或测试能发现；文档必须维护词表。

关系组件 Relationship 可接受但有代价

所有权/归属用 ECS 关系表达，清理由 linked_spawn 或系统负责。
变体
行动实体 → actor（ActionOf/ActionChildren，级联）；效果 → 宿主（EffectOf/OwnedEffects，级联）；槽位容器（Container.slots，数组、不级联）。
代表
action/ownership.rs / effect/ownership.rs / item/container.rs
  • 好处：查询"某 actor 名下"天然可表达；级联清理不用手写两遍。
  • 代价：容器用数组不走关系，所有权语义分裂成两种；跨关系查询仍是手写遍历。

B. 调度：一轮里谁先谁后

阶段化流水线 Pipeline 清晰

行动生命周期被固定成六段，扩展点是"插一个生成器/校验器"，不是改主函数。
变体
行动六阶段（Generate → Arbitrate → Tick → Validate → Execute → Complete）；核心结算链 20 步 .chain()；初始化链。
代表
action/entity.rs ActionPhase / system/mod.rs build_core_schedule / schedule.rs 4 个 ScheduleLabel
  • 好处：顺序是类型化契约（SystemSet）；每段职责单一。
  • 代价：段间大量 ApplyDeferred，隐式时序要靠注释维持；20 步链已触到 bevy 元组上限。

仲裁器 + 预算 Arbiter / Budget 清晰

同一 actor 一轮只执行一个行动，选择靠优先级全序；移动预算靠预占。
变体
优先级排序（同优先级按实体 index 平局）；Reservation::probe / claim / step 三态（试算不污染、成功才预占）。
代表
action/entity.rs 优先级常量 / action/validation.rs Reservation
  • 好处：确定性；"边试边预留"曾导致寻路污染，probe/claim 拆分是教训沉淀。
  • 代价：probe 与 claim 必须保持同一判定逻辑，否则出现"能走但没占到"的缝隙。

决策与执行分离 Decide / Execute 清晰

校验器只做"定案"，落地器只做"执行"；两者通过目标组件 + 意图事件连接。
变体
Decision::{Move,Attack,Cast,Throw,Stay}；意图事件三种（攻击/施法/投掷）再由结算系统消费。
代表
action/validation.rs apply_decision / action/settle.rs / events.rs
  • 好处：规则可单测；落地只有一个写 Position 的系统；"动作不同"没有长成 switch。
  • 代价：一次行动要跨两文件才能读懂；意图事件和消息缓冲需要同时更新。

延迟命令 + 双缓冲消息 Deferred / Double buffer 可接受但有代价

世界结构变化统一推迟；事件用 Message 双缓冲，轮末统一 update。
变体
Commands + ApplyDeferred；CoreEventBuffers 包 9 路事件，update_events_system 收口。
代表
system/mod.rs:53 update_events_system / action/entity.rs 调度段间 ApplyDeferred
  • 好处：系统顺序无关结构变化；事件不会跨轮残留。
  • 代价：新增事件类型必须同时改缓冲结构、update 与注册三处，漏一处就是跨轮幽灵事件。

C. 行为与生命周期：谁代表一次行动/一个效果

行动即实体 Action as Entity 清晰

一次行动是 actor 名下的瞬态实体，载荷组件说明"是什么行动"，完成后整棵子树回收。
变体
玩家/追/逃/游荡/等待五种生成器；载荷 Wait/Move/BasicAttack/Chase/Flee/Wander/CastSpell/ThrowAction；候选-激活（Candidate/ActiveAction/Ready）。
代表
action/entity.rs / action/ownership.rs:26
  • 好处：行动可查询、可中断、可级联清理；AI 与玩家共用一条链。
  • 代价：实体数增长（每行动一个实体）；调试要看两级实体。

效果即实体 Effect as Entity 清晰

中毒/治疗泉/buff 不是字段，是带宿主关系的实体，生命周期由效果系统所有。
变体
宿主效果（EffectOf 级联）；格子效果（CellEffectAt + 格索引，不挂宿主）。
代表
effect/status.rs Poison / effect/cell.rs CellEffectAt
  • 好处：不同效果的可视化/日志/清理统一；buffer 效果有落点。
  • 代价：死亡/转移要保证级联语义；格子效果另走索引，双轨。

单一写者 + 统一出口 Single Writer / Funnel 清晰

同一状态只有一个系统能写；跨类型伤害只有一个事件出口。
变体
位置只由 settle 写；生命/法力上限只由 apply_maxima 写；伤害出经由 DamageTakenEvent 收口（近战/法术/投掷都发）。
代表
action/settle.rs / rules/vitals.rs / events.rs:33 DamageTakenEvent
  • 好处：改一处不会出现两条赋值路径；仇恨/武器经验等消费方只订阅一个事件。
  • 代价：出口成为热点文件，新增伤害类型要记得接入。

D. 规则、时间与能力门控

策略族校验器 Strategy Validators 清晰

每种行动一个独立校验系统，按 ActionKind 过滤；新增行动 = 新增一个策略 + 一行调度。
变体
7 个校验器：move / chase / flee / wander / basic_attack / cast / throw；共享 Reservation 与失败语义。
代表
action/validation.rs:181-589
  • 好处：策略之间零依赖；可单独测；"同轮只定一个"由调度保证。
  • 代价：校验器之间共享状态（占位预算）是隐式耦合。

通用时长 Timer / Expiry 清晰

效果时长不各自为政：统一 EffectDuration 推进、统一到期回收。
变体
效果时长（effect 实体）；行动计时（ActionTimer，tick 推进）；两者都读 WorldClock.last_step_av。
代表
effect/duration.rs / action/entity.rs tick_action_timers_system
  • 好处：中毒迁移后"谁负责回收"只有一处答案。
  • 代价：tick 语义（跨多点结算）藏在消费者里，时长组件本身不结算。

标记组件作能力门控 Marker as Capability 可接受但有代价

AI 能力用零大小组件门控查询（CanChase 等），模板只描述列表。
变体
CanMove/CanChase/CanFlee/CanWander/CanBasicAttack/CanWait；Observable 显式标记信息栏候选；Player/Monster/Blocks 身份/过滤。
代表
components.rs / monster/spawn.rs attach_abilities
  • 好处：系统过滤器类型化，AI 生成器不需要知道物种。
  • 代价：能力有两处真源：模板的 abilities 列表 + spawn 时映射出的组件；新增能力要同时改枚举、映射、生成器。

E. 边界：内核如何接到外部（相邻 crate 的可借鉴模式）

契约 DTO + 装配器 Contract / Assembler 清晰

内核不输出 ratatui 类型，只输出 SceneFrame/UiView；extract 负责 world → DTO 的组装。
变体
渲染契约（render-api 叶子 crate）；页面视图枚举（Inventory/ThrowAim 由 extract 特判构建）；输入映射（Key → PlayerCommand / UiIntent）。
代表
render-api / presentation/src/extract/mod.rs / presentation/src/ui/mod.rs
  • 好处：前端可替换；tui 不依赖 ecs_core；契约版本可验证。
  • 代价：契约与内核存在两层模型，字段要手工同步。

前端接缝 Ports & Adapters（DsnX19） 清晰

主循环归 App::run_with，终端细节退到 Frontend 适配器。
变体
trait Frontend（poll_input/viewport/draw/pump/wait/finish）；TuiFrontend；测试用 HeadlessFrontend。
代表
src/frontend.rs / tests/frontend_loop_test.rs
  • 好处：主循环可无终端测试；错误能冒泡。
  • 代价：pump 是后端反向持有 App 的窄缝。

4张力与反模式：读代码时最该警惕的五处

1. 内容与运行时混在同一文件 需要处理

这是"内容 / 纯结构"拆分研究指出的核心问题。
  • item/container.rs：容器布局数据 + Container 组件
  • monster/template.rs：怪物卡数据 + MonsterKindId: Component
  • spell/mod.rs：法术数据 + 施法系统；rules/vitals.rs：曲线 + 系统
  • 后果：注册表"看起来是纯的"，实际依赖了带 bevy 的类型，无法独立成 crate。

2. SystemParam 聚合体变胖 可接受但有代价

用参数对象压参数个数，但把查询耦合藏进了一个结构体。
  • ThrowResolution 约 10 个字段；CoreEventBuffers 9 路事件；PlayerWorld/DamageSink/ChaseWorld 各 4–7 项。
  • 好处：函数签名可读；代价：字段增删牵动多个系统，测试要造整个上下文。

3. 能力双份：模板列表 vs 标记组件 可接受但有代价

MonsterTemplate.abilities 与 spawn 时的 Can* 组件是同一事实的两份表示。
  • 新增能力要改三处：Ability 枚举、attach 映射、生成器过滤器。
  • 测试能兜住，但内容卡与代码容易漂移。

4. 隐式顺序契约 需要处理

结算链顺序、ApplyDeferred 段、事件 update、装配桥先后全靠集中注册与注释保证。
  • 错误形态：新增系统插错段 → 同轮看不到死亡/仇恨/掉落。
  • 缓解：全部调度集中在 system/mod.rs、action/entity.rs、world/init.rs 三处，禁止分散注册。

5. 枚举占位与旧类型残留 可接受但有代价

历史演进留下"从未到达"的变体与已退役类型。
  • ItemKind 已退役；PageKind::ThrowSelect 从未进入；旧 tui::state::PageStack 已无消费者。
  • 风险：读代码的人会以为有第二条路径；清理应配合拆分 Step 1 一起做。

5与「内容 / 纯结构拆分」的关系

模式识别的结论与拆分研究（history 分支的 history/ecs-core-split.md（检索用））一致：组织结构本身是清楚的（流水线、单一写者、策略校验、注册表都成立），真正影响职责清晰度的是数据的归属——内容数据与运行时类型绑在同一文件、同一枚举里。

因此 Step 1 的目标不是"重写架构"，而是让模式 1–3（注册表 / 装配器 / 词表）能在一个不导入 bevy 的模块里独立解释。运行时模式（流水线、关系、效果实体、消息）保持不动。
